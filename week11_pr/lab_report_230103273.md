## Diagnostic notes
- False sharing: compare stride 1 with stride 16; a sharp improvement at larger stride is consistent with cache-line contention. The actual cache-line boundary must be checked against your CPU.
- Karp–Flatt: increasing values with p indicate growing non-parallel overheads; compare both strides rather than assuming all overhead is serial code.
- Strong scaling: speedup is limited by serial Stage A, process scheduling, and memory/cache effects. Weak scaling is sensitive to how Stage A grows with total N.
- Roofline: Python interpreter overhead means these are empirical Python-workload ceilings, not hardware peak FLOP/s. GEMM loop order changes locality; blocked tile size should be interpreted alongside actual L1/L2 sizes.
- Scheduling: C=1 increases lock traffic; very large chunks can leave a long tail. Select C* from the measured minimum wall time, not from a theoretical guess.
